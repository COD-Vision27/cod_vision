# 服务器端资产、标注与训练框架

状态：building。开发机只保存代码、配置与插件源文件；渲染、仿真和训练均在服务器运行。当前没有2027装甲参考，数据生产任务保持等待资产状态。

## 选型决策

Blender承载资产与场景，BlenderProc批量执行GPU渲染，SP Armor Labels补足项目自己的四点/颜色/编号输出。BlenderProc自带COCO/BOP writer，但它们不能直接等同于本项目22维模型契约，因此本项目需要专用writer。现有Bevy保留给后续闭环控制仿真，当前不将闭环仿真器的改造设为合成数据生产的前置条件。

核对的上游依据：

- [BlenderProc功能与运行模式](https://github.com/DLR-RM/BlenderProc)：场景加载、相机/光照/材质采样、RGB/深度/分割和标注输出。
- [BlenderProc版本定义](https://github.com/DLR-RM/BlenderProc/blob/main/blenderproc/version.py)：2.8.0。
- [BlenderProc Blender依赖](https://github.com/DLR-RM/BlenderProc/blob/main/blenderproc/python/utility/InstallUtility.py)：其配置的Blender版本为4.2.1。
- [Replicator官方能力](https://docs.omniverse.nvidia.com/extensions/latest/ext_replicator.html)：也支持随机化及自定义writer。当前选择Blender体系以直接承接建模资产和项目已有Blender接口；不是宣称其他方案不能完成任务。

## 插件与任务接口

插件源位于 `blender_addon/sp_armor_labels/`。面板的一次操作完成当前帧渲染和几何标注；服务器批处理直接复用同一 `bind_registry → capture → commit` 接口，不依赖界面。

资产注册表以实际模型对象和物理特征点对象建立关系，字段包括：资产版本、装甲实例根对象、显示变体对应的颜色/编号、四个关键点对象名称。空注册表是正常的building状态，不塞入旧灯条几何或猜测的2027点阵图。后续一旦建模完成，绑定四点即可产生几何真值，不要求旧模型先识别出新装甲。

单帧输出：RGB PNG、几何真值JSON、项目13列YOLO训练TXT。网络输出仍按原22维契约；36种颜色/编号组合只是标签编码，不替换成普通36类框检测器。同一次渲染提取相机、对象与四点状态；不以异步读取时刻拼接标签。遮挡或不完整四点当前拒绝整个不明确帧，遮挡训练策略仍是后续集成项。

## 流水线与服务器边界

`configs/pipeline.json` 定义服务器GPU、采样、资产路径、阶段产物和训练配置；没有绑定当前电脑或自动下载/安装环境的动作。`pipeline.py` 按以下阶段连接模块：

1. BlenderProc渲染＋插件标注。
2. 导入统一数据结构。
3. 按场景/轨迹分组，整理train/val/test及manifest。
4. 训练任务消费数据集，保存checkpoint。
5. 导出模块保持原推理输出接口。

执行要求服务器进程角色匹配，缺GPU时不回退CPU；资产状态未核实、场景未填充时不进入渲染。当前默认原IR权重初始化仅是训练后端的一种配置，是否从头训练/迁移学习留待新资产和实验设计确定，不依赖其现有识别能力。
